# Glyphshift 缺陷报告

> 测试方式：基于 2026-11-04 实测排查会话的真实监控数据模拟测试执行。
> 所有问题均有实测证据支撑；无法确认的信息统一标注「待补充」，未做推测性编造。

## 测试对象

- **Glyphshift 桌面软件**（版本号待补充）
  - 桌面壳：`glyphshift-desktop-shell.exe`（PID 13204）
  - 原生控制器：`controller-916eaa8c0c43.exe`（x64）、`controller-x86-6760d53fc98d.exe`（x86），按需启停
  - 注入组件：`runtime-234aac2c0def.dll`（约 2.9 MB）+ 适配器 DLL
- **目标软件**：Altium Designer Enterprise 25.4.2（`C:\Program Files\Altium\AD25\X2.EXE`，版本 25.4.2.15）

## 需求/预期

1. 选择字典并启用工作流后，应在数秒内稳定连接目标软件并开始界面文字采集/翻译。
2. 启用、停用过程不应影响目标软件的正常响应。
3. 字典内容只能由用户显式维护，不应被运行过程意外污染。

## 缺陷列表（按严重级别排序）

### GS-D-001 加载大规模字典时控制器约 15 秒激活超时，连接目标软件失败

| 字段 | 内容 |
|---|---|
| 编号 | GS-D-001 |
| 模块 | 字典加载 / 控制器激活 |
| 严重级别 | **致命**（阻断核心功能） |
| 问题类型 | 功能缺陷（超时处理不当）/ 性能 |
| 复现步骤 | 1. 启动 X2.EXE；2. 在 Glyphshift 中启用绑定「X2 字典」（10,606 条，约 1.2 MB）的工作流；3. 观察连接结果 |
| 预期结果 | 数秒内完成连接并开始采集 |
| 实际结果 | x64/x86 两个控制器进程启动后存活精确约 15.2s / 15.4s 即退出，采集记录 observedCount=0，连接失败；同环境下空字典（AD25.4.2）6.0s 内成功（observedCount=28），22 条裁剪字典立即可连，7,256 条去自映射字典可连 |
| 可能原因 | 字典解析/索引构建或注入握手在控制器内同步执行，耗时随字典规模增长，超过内置约 15 秒激活超时即被回收。阈值介于 7,256～10,606 条之间，精确阈值待补充 |
| 建议验证方式 | 用二分法构造 8k/9k/10k 条字典复测定位阈值；在控制器侧加日志确认超时常量与耗时分布 |
| 证据 | `monitor-20261104-134923.log`：13:55:11.818→13:55:26.317（15.2s，失败）、13:56:01.508→13:56:07.252（6.0s，成功）、13:56:41.957→13:56:57.144（15.4s，失败）；observedCount 0 vs 28 来自会话期间 run 记录快照（原始采集记录文件此后已被应用轮转删除） |

### GS-D-002 collectNewSources 把已翻译的中文界面文字回写字典，字典运行中自我膨胀并产生空翻译垃圾条目

| 字段 | 内容 |
|---|---|
| 编号 | GS-D-002 |
| 模块 | 采集回写（collectNewSources） |
| 严重级别 | **高**（GS-D-001 间歇性发作的直接放大器 + 数据污染） |
| 问题类型 | 功能缺陷（采集过滤逻辑）/ 数据污染 |
| 复现步骤 | 1. 启用任一 collectNewSources=true 的工作流；2. 正常运行一段时间；3. 对比运行前后字典条目数与内容 |
| 预期结果 | 仅采集目标软件出现的新原文词条，且不带空翻译 |
| 实际结果 | ① 22 条裁剪字典运行 97 秒内膨胀至 1,221 条（会话末期达 1,500 条）；② 去自映射字典从 7,256 条膨胀至 8,100 条，新增 844 条全部为空翻译；③ 初始为空的 AD25.4.2 字典被写入 24 条空翻译条目；④ 大字典中存在 3,350 条"译文=原文"自映射。字典膨胀后再次启用即触发 GS-D-001 超时——这解释了"有时能连、有时不能连" |
| 可能原因 | 采集侧未区分「原文」与「已被替换上屏的译文」，把翻译结果当作新 source 回收；回写时 translation 字段未填充，产生空翻译条目 |
| 建议验证方式 | 关闭 collectNewSources 后运行相同时长，核对字典条数不变、无空翻译条目；检查新增条目是否均为中文（译文特征） |
| 证据 | 实测字典快照：`dictionary-7247bd12`（8,100 条 / 844 条空翻译）、`dictionary-8f5a5234`（24 条全部空翻译）、`dictionary-d980e70e`（10,606 条 / 3,350 条自映射）；裁剪版 22→1,221→1,500 条为会话期间分析记录 |

### GS-D-003 启用/停用工作流时目标软件界面冻结约 10 秒

| 字段 | 内容 |
|---|---|
| 编号 | GS-D-003 |
| 模块 | 注入 / 卸载流程 |
| 严重级别 | **中** |
| 问题类型 | 性能缺陷 |
| 复现步骤 | 1. 启用绑定字典的工作流；2. 观察 X2 窗口响应；3. 停用工作流再次观察 |
| 预期结果 | 启停过程目标软件保持响应，无明显卡顿 |
| 实际结果 | 用户实测报告「启动运行和结束运行时软件会卡住约 10s 后恢复正常」。监控显示控制器启动段耗时约 6.8s（15:43:41.969→15:43:48.778）。精确卡顿时长待补充（hang-probe 探测脚本因 EnumWindows 回调作用域 bug 未捕获到 IsHungAppWindow 事件） |
| 可能原因 | 启动时需向目标进程注入 4 个模块（runtime DLL + 3 个适配器）并同步构建字典索引，阻塞目标进程 UI 线程消息泵；停止时执行反向卸载 |
| 建议验证方式 | 修复 hang-probe 脚本后重测精确卡顿时长；分别测试减少适配器数量、减小字典规模后卡顿是否缩短 |
| 证据 | `hang-20261104-154311.log` 控制器时序；用户实测反馈（约 10s） |

### GS-D-005 双 X2.EXE 实例并存，注入目标存在歧义

| 字段 | 内容 |

| 模块 | 目标进程识别 / 附加 |
| 严重级别 | **中** |
| 问题类型 | 功能缺陷（目标选择逻辑） |
| 复现步骤 | 1. 用户手动启动 X2.EXE（实例 A）；2. Glyphshift 活动后系统中出现第二个 X2.EXE 实例（实例 B，由 Glyphshift 壳进程拉起） |

### GS-D-006 首次启用周期无产出，需二次启用才生效

| 字段 | 内容 |
|---|---|
| 编号 | GS-D-006 |
| 模块 | 工作流启用流程 |
| 严重级别 | **中** |
| 问题类型 | 功能缺陷 |
| 复现步骤 | 1. 启用工作流；2. 观察首个控制器周期的采集产出；3. 再次启用对比 |
| 预期结果 | 首次启用即正常采集 |
| 实际结果 | 首个控制器周期存活约 6.8s 后退出且无采集产出；第二次启用后控制器存活 49.7s 并正常采集。是否 100% 复现待补充 |

## 附：整体结论

「有时能连、有时不能连」主链为 **GS-D-002（字典自我膨胀）→ GS-D-001（超 15s 超时阈值连接失败）**：字典规模随运行时间动态变化，能否连接取决于启用时刻的词条数，故表现为间歇性。建议优先修复 GS-D-002 并为 GS-D-001 增加超时豁免（大字典异步加载/索引预热）。
